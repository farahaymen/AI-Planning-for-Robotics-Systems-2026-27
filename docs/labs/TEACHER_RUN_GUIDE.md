# Teacher run guide: nine ARC laboratories

This file is for the teacher running the current nine-lab repository. The student reader remains `docs/ARC_Laboratories.html`. Use this guide to stage an experiment, explain each observation, give students a specific task, and retain evidence. **All commands below run in the Ubuntu course VM, never in Windows PowerShell.** Start each command from a terminal prompt. Do not type the sample prompt itself.

## Before the first class

1. If desktop login started `arc-setup` automatically, let that process finish first. Update and build the course once with `arc-setup --clean` when a clean rebuild is needed. This removes generated course build/install/log folders; it does not erase `src`, saved maps, bags or student source. Save source edits before updating. Wait for the final result. If setup fails in the offline suite, keep the first error in `~/arc_ws/.arc/offline-tests.log`.
2. In a **new** terminal, prepare the environment:

   ```bash
   source /opt/ros/jazzy/setup.bash
   source ~/arc_ws/install/setup.bash
   cd ~/arc_ws/src/arc-course
   ros2 pkg prefix arc_lab1
   ```

   The two `source` commands set up this terminal; silence is normal. `cd` selects the repository so relative `results/` and `models/` paths work. `ros2 pkg prefix` should print a path ending in `install/arc_lab1`. Repeat the three preparation lines **in every new terminal**. Once students have built `~/student_ws`, they also run `source ~/student_ws/install/local_setup.bash` after those lines when using their own package.
3. With no Gazebo, SLAM, RViz, teleop or Nav2 launch still running, check the VM:

   ```bash
   course-check
   course-smoke-test --headless
   ```

   The first checks installation and prints PASS/FAIL rows; the second starts the real simulation, waits for controllers, checks movement and sensors, then stops it. Look for passing **required** checks. A graphics warning can be a separate issue. If the second command fails, read `~/arc_ws/.arc/last-launch.log` before teaching a live simulation lab. The longer `bash scripts/course-lab-check` also runs the repository's offline tests. Do not run the smoke test over an already running class demonstration.
4. Make sure `~/arc_ws/maps/lab03_map.yaml` and its image exist before Lab 4 and Lab 5, and a trained `models/lab08_dense.zip` exists before the PPO part of Lab 9. These are produced in earlier labs. A precomputed example is acceptable for a teacher demonstration if labelled as such; students should still create and assess their own outputs.

**Terminal convention:** A holds a long-running simulation or publisher, B holds SLAM, Nav2 or a second node, and C holds short inspection commands. A command with `--once` returns by itself; `ros2 launch`, `ros2 bag record`, `ros2 topic hz`, teleop and `tf2_echo` keep running until Ctrl+C. Stop conflicting publishers before moving to a later experiment. `arc-clean` can clear leftover course processes after a failed launch. Do not delete `maps`, `bags`, `models` or student source while cleaning.

**How to judge an output:** Recorded numbers, map cell indices and learned success rates vary with the run. Confirm the stated *kind* of output and the measured value. Keep command text, a terminal excerpt, a screenshot or replay, and a one-sentence interpretation. No file generated by colcon under `build/`, `install/` or `log/` is a student source file.

Use `xdg-open PATH` in the desktop VM to open a generated `.html` replay or `.png` plot, for example `xdg-open results/lab04_astar/replay.html`. Use `cat PATH` for a short JSON report or map YAML. These are viewing commands; they do not rerun an experiment or create a model.

## Lab 1: messages, nodes, topics and a first student package

**Goal:** A synthetic distance source publishes on `/range`; a monitor receives it and reacts. No Gazebo window is expected.

| Run in a prepared terminal | Explain while running | Expected observation |
|---|---|---|
| A: `ros2 run arc_lab1 range_source` | Run an executable from a ROS package. Its node publishes a `Float32` message at 10 Hz. | Log says it is publishing at 10 Hz; A stays occupied. |
| C: `ros2 node list` and `ros2 topic list` | A node is a running component; a topic is a named message stream. | `/range_source` and `/range` appear; unrelated ROS topics may also appear. |
| C: `ros2 topic echo /range --once` | The CLI becomes a temporary subscriber. | One `data: <number>` reading, then the prompt returns. |
| C: `ros2 topic type /range` and `ros2 interface show std_msgs/msg/Float32` | A topic has a type and the type has fields. | `std_msgs/msg/Float32`, then `float32 data`. |
| B: `ros2 run arc_lab1 range_monitor` | A second node subscribes to the same stream. | Rate reports around 10 Hz in two-second windows. |
| C: `ros2 node info /range_monitor` and `ros2 topic info /range` | Inspect the receiver and count publishers/subscribers. | The monitor subscribes to `/range`; one publisher and at least one subscriber. |
| C: `ros2 param set /range_source amplitude 0.4` | The parameter changes new readings, without editing source. | Source readings range approximately 0.2 to 1.0 m; B warns when a reading is below 1.0 m. |

Show the arithmetic: the source publishes `amplitude * (1.5 + sin(k * 0.1))`. At amplitude 0.4, the bracket can range from 0.5 to 2.5. Restore `ros2 param set /range_source amplitude 2.0` afterward.

**Problem to solve together:** Stop A, restart with `ros2 run arc_lab1 range_source --ros-args -r range:=range_test`, and use `ros2 node info /range_source`, `ros2 node info /range_monitor` and `ros2 topic echo /range_test --once`. The source still publishes, but B eventually reports 0 Hz because it listens to `/range`. Ask students to find the name mismatch, then restart the original source. This demonstrates diagnosis by checking both ends of a connection.

**Each student builds:** In `~/student_ws/src`, create `robot_workshop` once with `ros2 pkg create --build-type ament_python --license Apache-2.0 robot_workshop --dependencies rclpy std_msgs`. In its inner `robot_workshop/` directory, write `distance_source.py` and `distance_alert.py` following Lab 1. Register `distance_source` and `distance_alert` under `console_scripts` in `setup.py`. Run `colcon build --symlink-install --packages-select robot_workshop` from `~/student_ws`, source `~/student_ws/install/local_setup.bash`, and run both student nodes. With the source stopped, inject `ros2 topic pub --once /distance std_msgs/msg/Float32 '{data: 0.25}'` and then a 1.0 reading. At threshold 1.0 only 0.25 should warn, because the rule is strictly `<`. Students keep their package source and the two-case evidence. The generated package metadata is edited only for dependencies and entry points; generated `build/install/log` contents are not edited.

**Pass check:** A student can name the publisher, subscriber, topic, type and field, run their own two nodes without importing `arc_lab1`, and explain the remapping failure. If no data arrives, compare topic names/types before reinstalling anything.

## Lab 2: a real frame, a moving Gazebo robot and feedback

**Goal:** The robot body actually travels in Gazebo; odometry and laser data explain what happened. An RViz wheel animation alone is not movement through the world.

| Run | Explain while running | Expected observation |
|---|---|---|
| A: `ros2 launch arc_description display.launch.py` | Xacro generates the URDF robot description; RViz draws it and the joint slider changes a joint. | Stationary body with visible model; turning a slider rotates a wheel only. |
| C: `ros2 run tf2_ros tf2_echo base_link laser_link` | Frames give distances a named origin and orientation. | Repeated fixed translation near `[0.100, 0, 0.120]`, identity rotation. A brief initial “frame does not exist” is a discovery delay if correct values then arrive. Press Ctrl+C. |
| C: `ros2 topic echo /joint_states --once` | Joint state is a message, not proof of body displacement. | Joint names and positions. |
| Stop A, then A: `ros2 launch arc_gazebo simulation.launch.py` | Gazebo computes motion and sensor readings; the launch also starts bridge and controllers. | Gazebo world with spawned robot. Wait for controllers to start; A stays open. |
| C: `ros2 control list_controllers` and `ros2 topic echo /odom --once` | Controllers must be active; odometry is measured local feedback. | Joint-state and differential-drive controllers are active; `/odom` shows pose and twist. |
| B: `ros2 run arc_course drive_distance --ros-args -p use_sim_time:=true -p distance:=0.6 -p speed:=0.15` | A command flows through `/cmd_vel`, a timestamping relay, wheel control and Gazebo; `/odom` closes the loop. | Body moves then stops; log contains `Completed: odometry displacement ... m` near 0.6 m. A timeout is a failure to investigate. |
| C: `ros2 topic echo /scan --once --qos-reliability best_effort` and `ros2 topic hz /scan` | Inspect a beam array and its observed arrival rate. | Changing plausible ranges; `topic hz` prints a rate until Ctrl+C. Invalid, frozen or all-minimum scans need diagnosis. |

In the TF command, a static transform can display timestamp 0.0 and remain correct. That does not mean Gazebo is advancing. In a headless VM, use `ros2 launch arc_gazebo simulation.launch.py headless:=true` and, in another prepared terminal, `rviz2 -d "$(ros2 pkg prefix arc_gazebo)/share/arc_gazebo/rviz/simulation.rviz"` to view the simulated ROS data. The laser uses sensor-data QoS; a reliable-only observer may not connect to a best-effort publisher.

**Each student builds:** Copy the provided `teaching/building/robot_workshop/robot_workshop/drive_distance.py` scaffold into their own package, write `robot_workshop/motion_rule.py` with `command_speed(travelled, target, speed)`, register `drive_distance` in student `setup.py`, and add `geometry_msgs`, `nav_msgs`, `sensor_msgs` and `python3-numpy` to the student `package.xml` dependencies. Rebuild and run their own command with `distance:=0.4`. Students then change the rule to slow down near the target and compare stopping error. They should describe why the driver also requires fresh odometry and a clear scan.

**Record for Lab 3:** With Gazebo running, C starts `ros2 bag record -o ~/arc_ws/bags/lab02_route /scan /odom /tf /tf_static`. In B run `ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -p use_sim_time:=true`, focus B and drive a safe route using its on-screen keys. Press `k` to request a stop, then Ctrl+C in B and C. `ros2 bag info ~/arc_ws/bags/lab02_route` should list the recorded topics and counts. The bag database is generated evidence; students do not edit it.

**Pass check:** Observe body movement, changed odometry, valid scan and a final distance report. If the static display works but Gazebo does not, inspect controllers, `/scan`, `/odom`, and `~/arc_ws/.arc/last-launch.log` rather than treating the wheel slider as a successful simulation.

## Lab 4: plan a route, follow it and inspect a saved map

**Goal:** Compare routes found by search with the path actually followed by a controller. The core is A*, PID and Pure Pursuit. The visual replay here is a small kinematic simulation, not Gazebo physics.

| Run | Explain while running | Expected observation |
|---|---|---|
| `python3 -m teaching.navigation --algorithm astar --controller pursuit --out results/lab04_astar` | A* chooses cells, Pure Pursuit turns the robot along the resulting route. | JSON report with `expanded`, `goal_error_m`, `trajectory_valid` and clearance; `replay.html`, `trajectory.png`, `trajectory.csv`, `path_cells.npy`. |
| `python3 -m teaching.navigation --algorithm bfs --controller pursuit --out results/lab04_bfs` | Compare fewest edges on this four-connected unit-cost grid. | A replay and report; compare path lengths and expanded counts with A*. Counts may vary with tie-breaking. |
| `python3 -m teaching.navigation --algorithm astar --controller pid --out results/lab04_pid` | Same planned route with a different steering calculation. | A new report and trajectory; compare goal error, route shape and clearance. |
| `python3 -m teaching.inspect_map --map ~/arc_ws/maps/lab03_map.yaml --out results/lab04_map_view` | Convert the actual YAML/image into occupancy and inflated planning grids. | `grid.png` labelled with row/column axes and `metadata.json`; choose two connected free cells from this image. |
| `python3 -m teaching.navigation --map ~/arc_ws/maps/lab03_map.yaml --start ROW COL --goal ROW COL --algorithm astar --out results/lab04_saved_map` | Replace both `ROW COL` pairs with valid indices from *this* map. | A replay and report, or an explicit error for blocked, unknown, too-close or disconnected cells. Never treat example indices as universal coordinates. |

Use actual numeric row and column pairs instead of the capital placeholders before running the last command. Open a replay with `xdg-open results/lab04_astar/replay.html` and read metrics with `cat results/lab04_astar/report.json`. The replay's map-local coordinates are not automatically odometry or world coordinates. Draw an inflated wall around an occupied cell and ask whether the robot's centre can pass through a one-cell gap. A path can be collision-free while its followed trajectory cuts a corner; check `trajectory_valid` and clearance, not just the planned line.

**Each student builds:** Write `search(blocked, start, goal, algorithm)` in `starters/lab04/planner_skeleton.py`; try `ARC_SEARCH=starters.lab04.planner_skeleton python3 -m teaching.navigation --algorithm astar --out results/lab04_student` after implementation. Fill the PID calculation in `starters/algorithms/control_skeleton.py`; run `ARC_CONTROL=control_skeleton python3 -m pytest starters/algorithms/tests/test_control.py -q`. Change one gain and justify what changed in the trajectory. A failed run on a blocked goal can be the correct result.

**Extensions when time permits:** `python3 -m teaching.navigation --algorithm theta --out results/lab04_theta` shows any-angle search; `python3 -m teaching.rollout --policy gap --seeds 500 --out results/lab04_gap` shows reactive local steering; `python3 -m teaching.extensions --out results/lab04_extensions` shows reachable frontiers and synthetic ICP alignment. Each `--out` path must be new. Frontier cells are reachable free cells next to unknown cells, not targets inside unknown space.

**Pass check:** Students can distinguish the search output from the tracked trajectory, identify at least one measured difference between controllers, and explain their own saved-map start/goal choice. Week 6 coursework draws on Labs 1–4; the extensions are not mandatory.

## Lab 6: value, policy and Q-learning on a visible grid robot

**Goal:** Compare known-model planning to a learned Q table. The replay is a numerical grid simulation, not ROS motion in Gazebo.

| Run | Explain while running | Expected observation |
|---|---|---|
| `python3 -m teaching.tabular --method value --out results/lab06_value` | Value iteration has access to known transition probabilities. | Printed JSON report including `successes` over 100 evaluated episodes; `policy.png`, `policy.npy`, `replay.html`. |
| `python3 -m teaching.tabular --method policy --out results/lab06_policy` | Policy iteration evaluates and improves a policy using the same model. | Corresponding report and arrows; ties can give different arrows with similar values. |
| `python3 -m teaching.tabular --method q --episodes 3000 --seed 0 --out results/lab06_q` | Q-learning updates one state/action entry from sampled transitions. | `q.npy`, `returns.csv`, `learning.png`, policy and replay; report describes 100 evaluation attempts. |

Open `results/lab06_q/replay.html` with `xdg-open results/lab06_q/replay.html` and read `cat results/lab06_q/report.json`. Draw a single transition on the board. Slip and random exploration make measured success variable.

**Each student builds:** Implement `q_update` in `starters/lab06/q_update_skeleton.py`; check it with `ARC_TABULAR=starters.lab06.q_update_skeleton python3 -m pytest teaching/tests/test_nine_lab_algorithms.py -q` and run `ARC_TABULAR=starters.lab06.q_update_skeleton python3 -m teaching.tabular --method q --episodes 3000 --out results/lab06_student`. **Pass check:** A student explains the update arithmetic, model-based versus sampled learning, and why an exploratory training return is not the same as greedy evaluation. The visible grid robot moves in `replay.html`; Gazebo is not required today.

## Lab 8: REINFORCE returns and PPO continuous commands

**Goal:** See a direct policy update on the grid first, then train a continuous-action navigation policy and inspect its numerical robot replay.

| Run | Explain while running | Expected observation |
|---|---|---|
| `python3 -m teaching.policy_gradient --episodes 3000 --seed 0 --out results/lab08_reinforce` | REINFORCE learns grid action probabilities from complete-episode returns. | Message `Saved policy and episode returns...`; `policy.npy`, `returns.csv`, `report.json`. This command does **not** write a replay HTML. |
| `python3 -m teaching.train_policy --reward dense_progress --steps 200000 --seed 0 --name lab08_dense` | PPO learns a continuous velocity policy; output is a model, not a ROS node. | CPU training logs and `Saved models/lab08_dense.zip and models/lab08_dense.json`; `runs/lab08_dense/` monitoring logs. Allow significant time or prepare this run before class. |
| `python3 -m teaching.rollout --policy ppo --model models/lab08_dense.zip --seeds 500 501 502 --out results/lab08_validation` | Evaluate a frozen model on held-out layouts. | Per-episode JSON in the terminal, `summary.json`, `episodes.csv`, trajectory plots and animated `replay_500.html`. Open `results/lab08_validation/replay_500.html` with `xdg-open results/lab08_validation/replay_500.html`, and read `cat results/lab08_validation/summary.json`. Calculate discounted returns from rewards [1,2,3] at discount 0.9: [5.23,4.7,3].
